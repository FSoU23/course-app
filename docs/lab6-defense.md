## Простое объяснение

Пользователь — аккаунт с постоянным id. Сессия подтверждает текущий вход.
Supabase SDK сохраняет и обновляет сессию; мы не записываем пароли/токены в свои таблицы.
`checking` нужен, чтобы не показывать личную страницу, пока вход ещё проверяется.
После регистрации сессии может не быть: сначала нужно подтвердить письмо.

RequireAuth управляет страницами. RLS защищает сами данные, даже при запросе без нашего сайта.
`owner_id` книги должен совпадать с `auth.uid()` из проверенной сессии.
`USING` определяет доступные старые строки; `WITH CHECK` проверяет новую строку.
UPDATE использует оба условия: нельзя ни изменить чужую книгу, ни передать свою другому владельцу.
Для UPDATE нужен SELECT, иначе строка не видна для изменения.
Нулевой результат изменения/удаления показывается как недоступная книга без раскрытия чужого id.

При выходе Library размонтируется; её книги и черновики исчезают. При входе другого
аккаунта новый экземпляр начинает с пустого списка. Старые запросы отменяются,
поздние ответы не меняют состояние и не запускают навигацию.

Если INSERT прошёл, но повторное чтение списка не удалось, мы сохраняем возвращённую
базой книгу на экране и предлагаем обновить коллекцию. Повторный INSERT не нужен —
это предотвращает дубликаты из-за ошибки чтения после успешной записи.

## Настройка и демонстрация

1. Применить миграцию ЛР 5, seed, затем новую миграцию ЛР 6 один раз.
   Старую миграцию не менять и не запускать повторно.
2. В Supabase разрешены email/password, подтверждение почты включено.
   Site URL и Redirect URL: `http://localhost:5173`.
3. Заполнить frontend/.env.local по .env.example; запускать сайт на этом же origin.
4. Зарегистрировать два своих адреса A и B через форму сайта, подтвердить письма.
   Аккаунт Dashboard Supabase и аккаунт нашей библиотеки — разные аккаунты.
5. Войти A, создать две книги, обновить страницу. Изменить одну, отменить другое
   изменение, проверить статусный фильтр. Сохранить URL книги A.
6. Выйти: личный URL отправляет на вход. Войти B: книги A не видны.
   Создать книгу B, обновить страницу; чужой URL показывает «Книга не найдена».
7. Вернуться к A: книги A сохранились, B не видна. Проверить отмену и подтверждение удаления.
8. Проверить Offline во время загрузки и сохранения, восстановить сеть и повторить.
   Ввод остаётся, повторный submit во время запроса не создаёт вторую книгу.

## Проверка реальных границ доступа

Проверки через Dashboard как postgres не доказывают изоляцию пользователей.
Нужны запросы с обычными сессиями A/B и публичным ключом, без service_role.
В собственной локальной отладке используйте общий клиент `getSupabase()`:

```ts
// Выполняется при входе B. Подставьте реальные тестовые id A.
await client.from('books').select('id').eq('owner_id', ownerA)
await client.from('books').update({ title: 'Проверка запрета' }).eq('id', bookA).select('id')
await client.from('books').delete().eq('id', bookA).select('id')
// Ожидаются пустые массивы: чужие строки скрыты.
await client.from('books').insert({
  owner_id: ownerA, title: 'Проверка владельца', author: 'Тест',
  genre_id: 'novel', added_at: '2026-11-10',
}) // Ожидается ошибка RLS.
```

После проверки вернуться к A и убедиться, что книга не изменилась. Временный
отладочный код удалить. Пароли, сессии и токены не копировать в отчёт или Git.
Фактически выполненные проверки и оставшиеся пункты указаны в progress.md.
